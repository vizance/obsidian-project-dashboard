## Context

0.5.0 發布前做了一次獨立資安審查。審查員是 Codex，只讀程式碼，對照 Obsidian 的開發者政策、外掛規範與安全說明。主代理逐項重現了 8 項發現，其中 1 項會讓 Obsidian 卡死。第 3 項（補週沒有上限）由同時進行的 `show-every-dated-task` 處理，因為那邊會重寫同一段程式；這裡處理其餘 7 項。

## Goals / Non-Goals

**Goals:**

- 任何行事曆內容或筆記內容都不能讓 Obsidian 卡住，也不能讓外掛寫到不該寫的地方。
- 外掛只動自己建立的鑰匙。
- 外掛卸載後不留資料、不再寫入。

**Non-Goals:**

- 把解析移到 Web Worker。
- 限制網址指向內網。
- 開發工具的套件警告。

## Decisions

### 重複規則：在 ical.js 找日期的迴圈裡計數

ical.js 的 `RecurIterator.next()` 用 do-while 迴圈找下一個日期，每一圈都會呼叫 `check_contracting_rules()`。在 `src/core/calendar.ts` 裡包裝這個迴圈：

- 每次呼叫 `next()` 時把計數歸零，每次 `check_contracting_rules()` 加一。
- 計數超過 200,000 就丟出外掛自己的錯誤。
- `collectRecurring` 接住這個錯誤，把該行程視為沒有更多次。

包裝只在這個檔案裡、只套在外掛自己打包的 ical.js 上，不影響其他外掛。

200,000 的理由：每日規則找一個不存在的日期，要掃 4 年才放棄，約 1,500 次；每秒規則找某個小時，一天最多 86,400 次。200,000 足夠涵蓋正常規則，同時能在一秒內結束。

替代方案一：Web Worker 加逾時。展開是在畫面重繪時同步進行的，改成非同步要重寫 General 列的資料流程，所以不採用。

替代方案二：事先檢查規則是否可能成立。組合太多，無法窮舉，所以不採用。

### 鑰匙：只覆寫外掛自己建立的

設定頁存連結時，ID 以 `project-dashboard-calendar-` 開頭才沿用；否則產生新的外掛 ID，把這列改指向它，舊鑰匙不動。刪除時的規則本來就只清外掛自己的鑰匙，維持不變。`add-calendar-row` 規格的設定頁文字同步改成這個規則。

### 完成標記：線性尋找再往前去空白

`toggleDoneLine` 改成：
1. 用沒有前置 `\s*` 的正規表示式找出 `✅ YYYY-MM-DD` 的位置。
2. 再用字串操作往前去掉緊鄰的空白。

輸出結果和現在完全相同，只是時間變成線性。

### 程式碼圍欄：照 CommonMark 記住字元與長度

`src/core/task-lines.ts` 判斷圍欄時：
- 記住開啟的字元（反引號或波浪號）與長度。
- 關閉行要用同一個字元、長度至少一樣，後面只能有空白。

讀取任務與寫入時的唯讀判斷，用同一個函式。

### 時區與回應大小

- 註冊時區時，用 `new ICAL.Component(vtimezone.toJSON())` 建立一份沒有 parent 的複本。
- 記下外掛自己註冊過的 TZID，`dispose()` 時逐一移除。
- `CalendarStore` 在解析前檢查回應文字長度，超過 20 MB（以字元數近似）就回報 `行事曆太大`。

### 連結欄：密碼欄、失敗即清空

連結欄改成 `type="password"`，並設定 `spellcheck=false`、`autocomplete="off"`。驗證失敗時清空欄位並顯示既有的錯誤訊息。成功時本來就會清空。

### 卸載：先存再停

`PluginDataStore.dispose()`：有排著的延遲存檔就立刻存一次，然後標記為已卸載，之後的 `updateSettings` 與存檔都直接忽略。`main.ts` 的 `onunload` 呼叫它。

## Implementation Contract

**行為：**

- 寫壞的重複規則在一秒內放棄，其他行程照常顯示。
- 外掛只覆寫自己建立的鑰匙。
- 取消勾選的時間是線性的。
- 四個反引號裡的範例不是任務。
- 卸載後時區登記處沒有外掛的時區，也不再存檔。
- 連結欄是密碼欄，失敗即清空。
- 超過 20 MB 的回應當作讀不到。

**介面與資料形狀：**

- 新的讀不到原因：`行事曆太大`。
- `PluginDataStore.dispose()`。
- 沒有新的設定。

**失敗與錯誤處理：**

- 重複規則超過上限：該行程靜默停止，其他行程不受影響。
- 回應太大：用 `行事曆太大` 回報，沿用既有的失敗顯示。

**驗收標準：**

- 規格 `dashboard-robustness` 每個情境都有測試，並確認在修正前會失敗。
- 主代理重跑重現腳本（2 月 30 日規則、4 萬空白、四反引號圍欄、鑰匙覆寫），全部解決。
- `npm test`、`npm run lint`、`npm run build` 通過。

**範圍內：** 上面 7 項，以及 `add-calendar-row` 規格裡設定頁沿用鑰匙 ID 的文字。

**範圍外：** Non-Goals 列出的所有項目，以及第 3 項（由 `show-every-dated-task` 處理）。

## Risks / Trade-offs

- [包裝 ical.js 的內部方法，未來升級 ical.js 可能失效] → 鎖定 ical.js 2.2.1；測試直接用「2 月 30 日」規則驗證，升級時測試會抓到。
- [密碼欄讓使用者看不到自己貼了什麼] → 貼上成功會顯示 `Link saved`；失敗會清空並提示重貼。
- [卸載時立刻存檔可能和 Obsidian 關閉同時發生] → 只存一次，存檔失敗也不重試，和現在的存檔失敗處理一致。
